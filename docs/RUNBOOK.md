# Operations Runbook

English-Language Assessment & Diagnostic Pilot. This is the operational half of `ARCHITECTURE.md`
Section 16 — what to do to run the pilot, and what is available if the free tiers behave as
Section 16 says they do.

It is deliberately short. Section 16 fixes the infrastructure at one Render web service and one
Supabase Postgres database, with no APM, no log aggregation service, and no queue, so there is very
little to operate.

---

## Deployment

The service is described by [`render.yaml`](../render.yaml) at the repository root, which Render reads
as a Blueprint. The equivalent dashboard settings, if the service is created by hand instead:

| Setting | Value |
| --- | --- |
| Environment | Node |
| Build command | `npm ci --include=dev && npx prisma generate && npm run build && npx prisma migrate deploy` |
| Start command | `node dist/server.js` |
| Instance type | Free |

Two parts of that build command are not incidental:

- **`prisma generate` must come before `npm run build`.** Nothing generates the Prisma client
  implicitly — there is no `postinstall` and no other script runs it — so `tsc` would otherwise
  compile against a `@prisma/client` whose generated types do not exist. On a developer machine this
  is invisible, because the client was generated by hand at some point; on a clean build it is a
  build failure.
- **`prisma migrate deploy` comes after the compile**, so a code error aborts the deploy without
  having already migrated the database. Both positions satisfy Section 16's "before the new instance
  starts serving traffic"; this one additionally keeps a failed build from leaving production on the
  old code against a new schema.

### Environment variables

Set in the Render dashboard, never committed (Section 16's table):

| Variable | Notes |
| --- | --- |
| `NODE_ENV` | `production` |
| `DATABASE_URL` | Supabase Postgres connection string |
| `OLLAMA_API_KEY` | Read only inside `src/ai/OllamaProvider.ts`; never logged or sent to a client |
| `OLLAMA_BASE_URL` | Ollama Cloud API endpoint |
| `SESSION_SECRET` | Signs both session cookies; at least 32 characters |

`PORT` is injected by Render. A missing or malformed variable is caught at boot by
`src/config/env.ts`, which names it and exits before binding a port.

### Migrations

`prisma migrate deploy` runs in the build step above and applies committed migration files only — it
never generates or resets. Migrations are never applied by hand against production (Section 16).

To check the state of the deployed database without changing it:

```bash
DATABASE_URL="<supabase-url>" npx prisma migrate status
```

### Provisioning a staff account

Migrations build the schema and insert nothing, and `prisma/seed.ts` is a development convenience
that a deploy never runs. **A freshly deployed instance therefore has no staff account at all** —
nobody can log in until this step has been done once. `FR-STAFF-002` requires staff accounts to be
created manually, and this is that manual step.

```bash
DATABASE_URL="<supabase-url>" node prisma/provision.ts
```

It prompts for the email and the password (the password is not echoed), prints the host and database
it is about to write to, and asks for confirmation before writing anything.

- **Idempotent.** The account is upserted by email, so re-running it rotates the password rather than
  colliding. This is also the only password-recovery path there is — there is no self-service reset,
  deliberately.
- **`DATABASE_URL` must be given on the command line.** The script deliberately does not read `.env`
  — `@prisma/client` loads it on import, so the script reads the variable *before* loading the client
  and refuses outright if it is unset. Without that ordering it would silently target the local
  development database.
- **Always confirm the printed target.** The confirmation step exists because an explicit connection
  string can still be the wrong one.

Cohorts are created in the application, at `/staff/cohorts`, by a signed-in staff member. With no
cohort existing, no student can start the assessment — the entry form will reject every code.

## Logs

Structured JSON on stdout, captured by Render's log viewer (Section 16). Every line comes from the one
logger in `src/config/logger.ts`. There is no log aggregation service.

Two lines are worth knowing by name:

- **`"event":"staff_submission_access"`** — one line per `GET /api/staff/submissions/:id`, including
  refusals, so an account walking a list of ids is visible. This is Section 13's one data-access log
  line, and it is an operational log rather than an audit table: nothing reads it back.
- **`"event":"request_failed"`** — an unexpected failure, carrying the full error and stack. The
  browser receives only a generic message (Section 11); this line is where the detail lives.

Fields named `apiKey` or `authorization` are redacted to `[Redacted]` at any depth the logger
examines (Section 13). See the note in `src/config/logger.ts` for exactly which depths that covers.

## Health check and the optional keep-warm ping

`GET /health` answers `200 {"status":"ok"}` when a trivial query reaches Postgres, and `503` with a
generic body when it cannot. It is not part of the API contract (Section 10 has no row for it) and it
takes no session.

### This mitigation is optional, and the pilot works without it

Section 16 is explicit that the ping is *"an **optional operational mitigation** available if the
pilot's actual usage pattern turns out to have idle gaps longer than a few days; it is not required
for the architecture to function."* Nothing below is needed for the MVP to work, and nothing below
should be set up "just in case". Reach for it only if the pilot actually shows one of these:

- **Render's free web service sleeps after about 15 minutes of inactivity** and takes roughly 30–60
  seconds to wake. The cost of not pinging is that the first visitor after a quiet period waits for
  that wake.
- **Supabase's free Postgres pauses after 7 days of continuous inactivity** and must be resumed from
  the dashboard. The cost of not pinging is a database that needs waking before the next assessment
  session. A Supabase pause does not delete data.

Ordinary pilot traffic hitting the app every few days keeps both warm as a side effect, which is why
this is a contingency rather than a requirement.

### If you decide to enable it

Point any free scheduler at `GET /health` every 10 minutes. A GitHub Actions workflow is the example
Section 16 gives, and it introduces no new infrastructure — GitHub Actions' free tier triggering an
endpoint that already exists:

```yaml
# .github/workflows/keep-warm.yml — add only if the pilot shows an idle-gap problem.
name: keep-warm

on:
  schedule:
    - cron: '*/10 * * * *'
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: Ping /health
        run: |
          curl --fail --silent --show-error --max-time 90 "https://<service>.onrender.com/health"
```

Notes:

- `--max-time 90` is deliberate: the ping's own purpose is to wake a sleeping service, and a timeout
  shorter than Render's 30–60 second wake would report a failure for a request that is working.
- `--fail` makes a `503` — the database being unreachable — a failed run rather than a silent success.
  That is the difference between this and a check that reports healthy no matter what.
- Do not add this workflow in a repository where Actions is unavailable; the runbook entry is the
  deliverable, and Section 16's $0 constraint is what rules out a paid uptime monitor.

## Backups

Supabase's free tier has no automated backups. Given the pilot's data volume, Section 16 recommends a
manual `pg_dump` before major milestones (for example, the end of data collection) as a zero-cost
safety net. This is an operational recommendation, not infrastructure.
